# 24. Reading Teams from files

Date: 2026-11-07
Status: Accepted (DEV-38, first built in DEV-62), amended by DEV-66, DEV-63 and DEV-118 (decided 2026-11-15, built in part: DEV-106, DEV-130, DEV-131, DEV-132, DEV-133, DEV-134, DEV-135, DEV-136 and DEV-137 so far)

## Context
ADR 6 and ADR 10 promise a "file in, Team out" pipeline for uploaded Teamsheet PDFs and screenshots of Replica Teams, but left open how files are read. The files differ a lot. A Teamsheet filled in on teamsheet.gg keeps its 151 form fields (`f0` to `f150`, `docs/research/vg-team-list-pdf.md`), so it can be read exactly, with no OCR. Scans, photos and in-game screenshots can't. Self-hosted installs come first (ADR 2) and need no configuration beyond the database (ADR 15).

## Decision
- **Reading a Team makes a draft, never a saved Team.** The draft opens in the Team builder (later, the Opponent's Team form) for the User to review and save. What the reader isn't sure of is flagged on that Pokémon build, in its slot and its editor, so the flag follows it when the Team is reordered. Flags about the Team as a whole, such as its Replica Team ID or a missing screenshot, are listed above its Pokémon (DEV-126). On save the draft passes the same checks as any other Team (ADR 14).
- **Reading is stateless.** The file is read and discarded: never stored, never logged. Only reading a Teamsheet already stored as an attachment (ADR 6, DEV-37) depends on storage.
- **Online only** (ADR 17). The control is disabled while offline.
- **Digital PDFs first, read in core.** `packages/core` reads teamsheet.gg's form fields with pdf-lib and does no I/O. It prefers the staff page, which has stats, and falls back to the opponents page. "Battle Team Number / Name" becomes the Team's name. Player details on the sheet are ignored and never written into Account settings. A PDF without that layout is refused as not a recognised Teamsheet. MyVGC's own export is read the same way (ADR 25), which a round-trip test in `packages/core` keeps (DEV-66). Other producers (RK9) are added once a sample is in hand.
- **Names become Showdown IDs through the Champions data.** A name that doesn't match leaves the field blank, with a flag giving the text that was read, rather than refusing the whole file.
- **Stat values become Stat Points by working ADR 19's formula backwards** with the species' base stats and the Stat Alignment. On a lowered stat, rounding down often lets two Stat Points values give the same stat value (Kingambit's Adamant SpA is 72 with 0 or 1). They make the same Pokémon, so the smallest is used without a flag; flagging would mark almost every Team read. A stat value no Stat Points can give gets 0 and a flag. Blank stat boxes leave Stat Points at 0.
  - When a file shows both a stat's value and its Stat Points, the value is worked out again from them and compared exactly (DEV-121). If the stats that don't match all fit one other Stat Alignment, the Stat Alignment is flagged, naming the one they fit, but isn't changed. Any other mismatch flags that stat. The numbers check the Stat Alignment and never choose it, so a misread number becomes a flag, not a wrong Stat Alignment. Built in DEV-135, in `readBuild`, so it applies to any reader that gives both; the five neutral Stat Alignments count as one there, named Serious. With no Stat Alignment, only HP is checked.
- **Images use an AI vision model, opt-in.** Screenshots of the User's own Replica Team (its "Moves & More" and "Stats" tabs) and of Pokémon detail screens are read by Anthropic's API behind a small reader interface in `apps/api`. A read takes 1 to 8 images: the two tabs plus a detail screen for each Pokémon (DEV-122). Images can be PNG, JPEG or WebP, up to 7 MB each, so each fits under the API's 10 MB limit, which applies once the image is base64-encoded. It's configured by `ANTHROPIC_API_KEY` and an optional `TEAM_READER_MODEL` (default `claude-haiku-5-5`, DEV-125: it read the samples exactly as well as Sonnet 5.5 at about 1/17 of the cost), with an optional per-User `TEAM_READER_DAILY_LIMIT` (unlimited when unset). With no key the image upload is hidden. The upload says the image is sent to Anthropic and not kept. No local OCR: it reads game UI poorly. Photos of a paper Teamsheet are no longer supported (DEV-118, built in DEV-133): the reader labels one unsupported and reads nothing from it, and the upload asks only for the supported screens. A paper Teamsheet is read from its PDF instead. Built in DEV-63 against a stubbed provider. DEV-102 checked it against the real model, and DEV-118 settled what real screenshots need.
  - The model returns, as structured output, only the words and numbers it sees (`seenTeamSchema` in `packages/core`). Core then matches names and works out Stat Points exactly as for a PDF, with the same flags, plus a flag on any field the model says was hard to make out. Stat Points shown on the image win over stat values.
  - What the model returns (DEV-120):
    - the Battle Team name and the Replica Team ID as separate fields;
    - each Pokémon's nickname and gender;
    - the stats its ▲/▼ arrows raise and lower;
    - whether its held item was shown;
    - the fields where the images disagree;
    - what kind of screen each image is.

    It is told the layout of each supported screen. It never returns the Trainer Name in Game, which is ignored like a PDF's Player details. It merges a Pokémon seen on several images into one. The Replica Team ID goes into the Team's Replica Team ID (DEV-67), never its name; an ID that isn't valid is left blank and flagged. No supported screen shows a Battle Team name, so the Team's name is usually left blank, with no flag, for the User to fill in.
  - The Stat Alignment comes from its name on a detail screen, or else from the arrows, looked up in the 20 Stat Alignments that raise one stat and lower another (DEV-121). If a Stats tab was read and a Pokémon has no arrows, it gets Serious with no flag: the five neutral Stat Alignments make the same Pokémon. This assumes the game shows no arrows for a neutral one, which no sample has confirmed yet (DEV-128). Arrows that can't be a Stat Alignment leave it blank, with a flag giving what was seen and the "worked out with no Stat Alignment" flag on its Stat Points. Built in DEV-135: the model returns `raisedStat` and `loweredStat` from the arrows on either screen.
  - The species is never swapped with the nickname (DEV-124). A nickname that names a species the stats fit exactly, when the read species doesn't fit, flags the species. Gender chooses the form of Meowstic, Indeedee and Basculegion; with no gender read, the species is flagged. A nickname equal to the species as read is dropped, and the Teamsheet export never shows nicknames. Built in DEV-134: a form named in the species text wins over the gender, with a flag when they contradict. Since DEV-163, a Male or Female after the species name, as a detail screen writes these three ("Basculegion Male"), counts as a named form. The nickname's check was built in DEV-136, with the numbers check's comparison: it counts only a nickname that is a species' own name, not one of Showdown's aliases, and when it flags the species it replaces the numbers check's flags on the stats, since the species is what to check.
  - A field no image showed (held item, ability, moves, Stat Alignment, stats, Replica Team ID) gets one flag for the Team, naming the screenshot that would fill it, plus a short flag on each Pokémon it affects (DEV-126, built in DEV-137). A Stat Alignment counts as shown when a Stats tab was read. Two fields of one screenshot row missing together, such as the Stat Alignment and stats, get one flag on the Pokémon. A field the images disagree on gets a flag on that Pokémon in place of the "hard to make out" one. Nickname and gender are optional, so they're never flagged as missing. An image that isn't a supported screen is flagged and nothing is read from it. If no image is supported, the read fails. Built in DEV-133: the model labels each image `replicaTeamMoves`, `replicaTeamStats`, `pokemonDetail` or `unsupported`, in upload order, and `readSeenTeam` gives the flag and the error.
  - The web app scales each image to at most 2576 px on the long edge before upload. That's the largest the model reads, so it costs no accuracy (DEV-119). It then re-encodes them as JPEG at quality 0.9, named with a `.jpg` extension, which cuts a full set from about 26 MB to about 3 MB. JPEG read every measured field as well as PNG (DEV-122, DEV-132), the ▲/▼ arrows included: in DEV-135's accuracy run both formats got every Stat Alignment from the arrows right in every run. If shrinking fails, or doesn't make the image smaller, the original is sent. The server never resizes.
  - An image's type comes from its first bytes, not its name. The images are never stored or logged; a failed read logs only the provider's error class and status.
  - Stat Points shown on the image win stat by stat; the other stats are worked out from their stat values.
  - One read is one request: the SDK doesn't retry. With `fallbacks: "default"`, a refused request can fall back, on Anthropic's side, to a model chosen for that refusal. Haiku 5.5 has no such fallback, so with the default model a refused read simply fails (DEV-125).
  - The daily limit counts reads per User per server day in `image_reads`, a count with nothing about the images in it. A read the provider fails isn't counted. A read that finds no Pokémon, or no supported screen, is counted, since it was paid for. This is the one piece of state image reading keeps.
  - It reads into a new Team only. The Round form's "Read their Teamsheet" (DEV-64) stays PDF-only for now.
- **Words:** code and UI say *read* and *reader*. *Import* stays reserved for pastes and the Data export (ADR 23).

## Consequences
- teamsheet.gg PDFs work on every install with no configuration, and the reader is unit-tested against a real teamsheet.gg file (with its Player details replaced).
- Image reading costs money per read and sends files to a third party, so it stays off unless an operator turns it on. The hosted service sets the daily limit.
- teamsheet.gg's field names are meaningless and could change. A changed layout is refused, not misread, and the fixture is replaced from a fresh download.
- Image reading is judged by `pnpm accuracy`, which runs the real model on committed fixture screenshots and must match each one's expected draft exactly (DEV-123). It never runs in CI. A change to the reader's instructions, `seenTeamSchema`, the default model or the web app's image shrinking shows a run before and after the change. The fixtures are the maintainer's own screenshots, with the Trainer Name in Game painted over, not User uploads, so reading stays stateless.
- A changed game screen can make reads worse without any error. The accuracy check and the flags for missing fields are how that shows up.
