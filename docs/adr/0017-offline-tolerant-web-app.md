# 17. Offline-tolerant web app with a queued-write outbox

Date: 2026-11-04 (amended 2026-11-05 for each species' own abilities, DEV-51, and base stats, DEV-50, and Note entries, DEV-35, and Data export, DEV-39; amended 2026-11-11 for list search, DEV-82; amended 2026-11-23 for v0.3.0's scope, the outbox's own store, updates and iOS, DEV-160; amended 2026-11-24 for a wider offline scope, DEV-202)
Status: Accepted

## Context
Roadmap principle: phone first. A User logs a Round between Rounds at an event, in venues that tend to lack a signal (the project owner's experience). Today the web app cannot start without the server: the auth middleware aborts every navigation with a 503 when the session check can't be reached. A failed save also loses the Round.

We considered full local-first (a client database as the source of truth, plus a sync engine). The research in `docs/research/local-first.md` found it larger than the need. It adds a service to Compose, bends ADRs 4, 8, 11, 13 and 15, and leans on immature pieces (TanStack DB is a release candidate, PowerSync's Vue composables are Beta and its Nuxt module Alpha, Electric Cloud is winding down, PGlite's browser storage doesn't work in Safari). The data is private to one User, so conflicts only arise when the same User uses two devices. The offline need comes from the owner's experience, not measured data.

The iOS research for v0.3.0 (`docs/research/ios-offline-web-apps.md` on the branch `research/dev-159-ios-offline-web-apps`, DEV-159) found three things this ADR first got wrong or left out. TanStack Query's persister deletes the whole saved client, paused mutations included, once it is 24 hours old or its version string changes. On an iPhone, a Home Screen web app starts with empty storage (only cookies are copied) and a Safari tab's storage is deleted after 7 days without a visit. And an installed app only picks up a new service worker on a cold launch.

The first iPhone test (DEV-161, 2026-11-24) showed that the first offline scope was too narrow. At a venue the Tournament often isn't in the app yet, and a Tournament could only be created online, so no Round could be logged against it. The maintainer asked for the app to be as usable offline as practical (DEV-202).

## Decision
Make the web app offline-tolerant, not local-first. The server and Postgres stay the only authority; the browser keeps a cache and a queue of pending writes.

- **Offline scope.** Every write that is a plain save works offline through the outbox. The User can open the app, read cached pages, and search the Tournaments, Teams and Opponents lists. They can also:
  - Create, edit (details, Placement, Championship Points) and delete a Tournament, and set or remove their Team for it.
  - Log, edit or delete a Round with its Games, the Opponent's Team and Age Division (all sent in the Round, ADR 21, ADR 22 and ADR 30), with the Record updating.
  - Create, edit (display name, Aliases) and delete an Opponent, and add, edit or delete their Note entries.
  - Build, edit and delete a Team.
  - Change their player details and list styles.

  The rest stays online-only, because it needs the server's code, the model or a file the server makes or keeps: sign-up, login, account recovery and passwords; reading a Team from files (ADR 24); paste import; the Teamsheet attachment and Teamsheet export (ADR 27); merging Opponents (DEV-36); Data export and import (ADR 23); and the dashboard and Statistics, which show only what is cached.
- **Teams are checked on the server.** Checking a Team needs Showdown's data, which stays out of the web bundle (see Reference names). A Team built or edited offline is queued unchecked and checked when it is sent. If it is invalid (for example, a name that isn't in Champions), the write is rejected like any other 400: it stays visible with the server's message so the User can fix or discard it. A Team that breaks its Regulation's rules is saved with warnings, as online (`0018-warn-about-illegal-teams.md`). Online, the Team builder keeps checking as the User builds.
- **List search runs in the browser.** The Tournaments, Teams and Opponents lists search the list already loaded, with a typo-tolerant pure function from `@myvgc/core/search`, so search works offline. The Opponents list fetches its Opponents up front for this, rather than sending each query to the server. The Round form's Opponent picker keeps using the server search (`GET /api/opponents?q=`) online, since it shows only a few suggestions. When the server can't be reached, it searches the Opponents already cached on the device with the same search function, and the User can still add a new Opponent.
- **Hono stays the only write path.** Writes use the existing routes. Tournaments, Rounds, Opponents, Note entries and Teams accept client-generated UUIDs (as does the new Opponent a Round adds), and creates are idempotent: replaying an id returns the existing row with a 200, and an id held by another User answers 409. Deletes are idempotent too: deleting something already gone, or not the User's, answers as done and removes nothing of anyone else's. An edit of a record that no longer exists still answers 404, since the server can't tell deleted from never existed; the outbox treats that as settled.
- **Server settles conflicts per record.** The server's version wins. If a replayed Round collides on its Swiss round number and the User didn't type that number (the client leaves `roundNumber` out), the server assigns the next free one; otherwise it answers 409 and the User resolves it. A Top cut stage already logged also answers 409. These 409s name the field, like a 400, so the Round form shows the message next to it.
- **Outbox.** Pending writes live in the app's own outbox, a small module that keeps each request in its own IndexedDB store, with no expiry and its own format version. A change is written there before the User sees it as saved on this phone. TanStack Query persists only the query cache. Writes on one Tournament run in series, as do writes on one Opponent (including its Note entries) and on one Team. A write that refers to something created offline, such as a Round in a new Tournament or a Tournament's Team that is itself new, waits until that create has been sent. Replay runs when the app opens, becomes visible or comes back online, and on a timer while writes are pending and the page is visible, never from the service worker (Background Sync is Chromium-only, and Safari has none). `online` and `navigator.onLine` are only hints: a failed or timed-out request decides that the server can't be reached. A write rejected by validation stays visible so the User can fix or discard it; a write that gets a 401 stays queued until the User logs in again. Nothing is dropped silently.
- **App shell.** A service worker precaches the generated SPA (`@vite-pwa/nuxt`, which a spike confirmed builds and serves the shell offline on Nuxt 4.6.4). It never caches `/api/*`; API data lives only in the Query cache. The manifest opens the app `standalone`, Hono serves `sw.js` from the site root with `Cache-Control: no-cache`, and `/` answers 200, never a redirect.
- **Updates.** A new version is never loaded on its own (`registerType: 'prompt'`). The app checks for one whenever it becomes visible, since an installed iPhone app only checks on a cold launch, and tells the User when one is ready; the User chooses when to reload, so a half-filled form isn't lost. Each change is in the outbox before it shows as saved, so pending writes carry over an update.
- **Auth.** When the session check can't reach the server, the app uses the last known User stored on the device instead of showing the 503 page. A reply of "logged out" still logs out.
- **Reference names.** One endpoint (or build-time JSON from `packages/core`) returns display names for species, moves, items and abilities, plus each species' or form's own abilities, base stats (for stat values) and types (`typesBySpecies`, so a Mega has the Mega's), and each move's own type (`moveTypes`) and power and accuracy (`powerAndAccuracy`, which leaves out status moves), about 31 KB gzipped, and is cached for pickers. Types and power and accuracy are worked out from the species and moves, never stored, like stat values: Team responses, Team snapshots and the Data export don't carry them. The 18 types and their names are hard-coded in `@myvgc/core/schema`, like the Stat Alignments (DEV-217, DEV-222). `@myvgc/core` stays out of the web bundle, and ADR 14 still holds (IDs stored, names looked up). Paste import keeps validating on the server.
- **Local data is per User and disposable.** The cache is keyed by user id, cleared on logout, and has a "clear data on this device" action. The app asks the browser for persistent storage. The cache carries a version string that is bumped when API shapes change; the outbox doesn't, so a bump never drops a pending write.
- **iPhone.** The installed Home Screen app is the place to log offline. It starts with empty storage, so it needs one launch with a connection before it can start offline, and the app says so. A Safari tab works too, but iOS deletes its data after 7 days without a visit.

## Consequences
- No new containers, licences or client database. Compose, the image and the tests (ADR 13: Vitest plus `app.request()` against PGlite) stay as they are. The outbox logic is a small pure module with Vitest tests, which needs a `test` script in `apps/web`.
- Contradicts no ADR. It supplements ADR 5 and ADR 7, because accounts and sessions still exist everywhere.
- DEV-32 grows by client IDs, idempotent writes and the offline Round-logging flow. DEV-35's Note entries get client IDs and idempotent writes; queuing them waits for the outbox (DEV-48). They are changed and deleted by ID alone, so a change queued before a merge still reaches the Note entry on the survivor. DEV-33 needs the names endpoint. DEV-39 (JSON export) matters more, since data now sits on phones.
- Account deletion removes server rows at once, but a device's local copy is only wiped when it next connects and sees the deletion. Settings' Your data section says so, next to "Clear data on this device". On a shared device, anyone can read the cache until it is cleared.
- Browsers may evict storage, so a queued write can be lost on a device that is never reopened. The persistent-storage request reduces this risk but doesn't remove it; on an iPhone, only the installed app is likely to get it.
- The session still lasts Better Auth's default 7 days (decided 2026-11-23). Offline, the app still opens with the last known User; once the session has expired, pending writes wait for the User to log in again.
- Two devices still only agree eventually, not live.
- A Team built offline may turn out to be invalid only once it is sent. Teams are usually built before an event rather than at the venue, so this is accepted rather than putting Showdown's data on the phone (DEV-202). Teams need client-generated ids and idempotent creates, like Tournaments.
- Not yet tested on a device: the iPhone behaviour above comes from documents, not a test. DEV-161 checks it on the maintainer's iPhone over HTTPS, since iOS won't register a service worker on a plain-HTTP LAN address.
- Move to full local-first (a new ADR that amends 4, 8, 11, 13 and 15) only if one of these happens: data lost at events despite the outbox, a need for live agreement between devices, a decision to offer local-only use (which would also contradict ADR 5), or the sync pieces maturing (TanStack DB GA, PowerSync's Nuxt module leaving Alpha, Safari-ready PGlite). The idempotent API built here is the same prerequisite a later sync engine needs.
