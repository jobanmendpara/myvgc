# Flaky tests

Tests that have failed and then passed on a rerun with no change. Record each sighting here, so a test that keeps flaking can be filed and fixed.

- On 2026-11-11 the DEV-95 agent saw `packages/core/test/teamsheet-writer.test.ts` "reads back as the same Team" fail once, then pass on reruns. The cause is unknown and nothing was filed. (Superseded 2026-11-11: filed as DEV-101 that day, and the cause found; see below.)
- On 2026-11-11 the DEV-101 agent reproduced it. Alone the file never failed: 301 in-process repeats (`--repeats 300`) and 200 fresh runs, 8 at a time, all passed. Running the whole core suite 60 times while two API suites ran alongside, as when agents run `pnpm test` side by side, gave 9 failures, every one "Test timed out in 5000ms"; the round trip took 4.3 s at the median and up to 6.1 s, against about 0.35 s idle. Other `writeTeamsheet` tests timed out too. No run gave a wrong result, so export and reading are deterministic and the tests share no state.
  - Cause: Vitest's default 5 s limit against CPU-bound PDF work (each export embeds and deflates the full DejaVu Sans, ADR 28; the first test also loads the Champions data) on a shared CPU.
  - Fix (jobanmendpara/myvgc@2b03b45): the `writeTeamsheet` and `readTeamsheet` describes allow 30 s, with the reason beside them, like the API's 30 s for PGlite. Under the same load the next 60 core runs all passed, the slowest round trip taking about 7 s.
- On 2026-11-15 the DEV-113 agent's first local `pnpm test` had 4 API test failures: team-library "lists only the User's Teams", two in teamsheet-export, and tournament-team "starts with no Team". They passed on a rerun with no change. Four other implementers were running tests at the time (see the [2026-11-15 Refactor round](refactor-round-2026-11-15.md)).
  - The cause is unknown: the agent piped the output through `grep`, so the failure messages were lost. The chief-of-staff's retro on DEV-113 (subagent report, 2026-11-15) found that every implementer that round filtered its test output the same way. It likely matches the DEV-101 shared-CPU timeout pattern above (teamsheet-export does CPU-bound PDF work), but that is unconfirmed. Nothing was filed for the tests themselves; DEV-144 asks agents to keep the full output in a scratchpad log before filtering it.
- On 2026-11-17 the DEV-142 agent's first local run of the API tests had 7 tests time out at 30 s, in data-export, opponent-teams, opponents, replays, rounds, teams and tournaments. All passed on a rerun with no change. Three implementers were running at once (see the [2026-11-17 Refactor round](refactor-round-2026-11-17.md)).
  - This time the agent kept the full log before filtering, as the brief asked, so the cause is confirmed: tests timing out on a busy machine, with no wrong result. This is the DEV-101 shared-CPU pattern above, now hitting the API's 30 s limit for PGlite. Added to [DEV-146](https://linear.app/mendpara/issue/DEV-146) (cut CI time for the API tests) as evidence on 2026-11-17.

- On 2026-11-25 the DEV-222 agent saw the smoke test "a Tournament created and deleted with no signal is never sent" (desktop) fail once in CI on PR #380, then pass on Playwright's retry. The same run also failed for a real reason: the smoke test read the names cache key `myvgc-names-v3` by name (fixed in the PR). Nothing was filed for the flake. It is the first sighting.
- On 2026-11-25 the DEV-224 agent saw the same smoke test fail on the phone project of PR #384's first run, on the first try and on Playwright's retry: the Tournament page never loaded offline. Rerunning the failed job passed. Two sightings on unrelated PRs in one day, so the chief-of-staff filed [DEV-231](https://linear.app/mendpara/issue/DEV-231).
  - On 2026-11-25 the DEV-231 agent found the cause in the failed run's trace (PR #384, run 45680165731, attempt 1). The test cut the signal while the service worker was still installing: it had fetched `_nuxt` files up to `DwmZ…` in alphabetical order, so the chunks for the Tournament page (`DXI-E_Aj.js`, `G8yzh3Nm.js`) failed with `ERR_INTERNET_DISCONNECTED`. Nuxt then reloaded `/tournaments/<id>`, and with no active service worker that failed too. The service worker keeps some 690 files (100 `_nuxt` files, 382 Sprites, 166 Item icons, 18 Type icons), and the Item and Type icons added by DEV-225 that day made its install longer. This test cut the signal soonest after sign-up, so it lost the race first; seven other offline tests went offline without waiting either.
  - Loop: a throwaway copy of the test that delayed every non-API request by 20 ms failed 3 of 3 on the phone project, with CI's error. Waiting for `navigator.serviceWorker.ready` before going offline passed 6 of 6 under the same delay.
  - Fix: a `goOffline(page)` helper in `e2e/tests/smoke.spec.ts` waits for `navigator.serviceWorker.ready` before `setOffline(true)`, and the eight offline tests that didn't wait use it. With it, the 11 offline tests passed 66 of 66 locally (both projects, 3 repeats, 6 workers). Not an app bug: a User who loses the signal within a second of their first visit can't expect pages the service worker hasn't kept yet.
  - On 2026-11-25 the v0.3.0 Release workflow (run 45688979530, tag at `jobanmendpara/myvgc@e3b3d94`) hit it a third time, on the phone project, first try and retry, with the same error. The tag predates the fix (PR #396, merged 20:02 UTC); rerunning the failed job passed.
